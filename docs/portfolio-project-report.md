## 2. 作品集 Hero 文案

### 项目标题

**Possibility OS**

### 英文副标题

**Interactive Career Stories**

### 中文主标题

**把职业介绍，变成一段可以亲手推进的工作故事**

### 项目摘要

Possibility OS 是一个面向年轻人的互动式职业体验平台。它不通过职业测试告诉用户“你适合什么”，也不把岗位知识做成课程，而是让用户进入一个模拟工作环境，亲自处理模糊信号、与不同角色协作、做出取舍，并最终产出一份真实可见的工作成果。

第一阶段完成了两条职业故事：产品经理体验让用户把一个模糊问题推进成 PRD、原型和数据迭代；HRBP 体验让用户从一封主管邮件出发，通过多方核实、员工面谈和行动回访，把个人标签重新还原为一个可以被组织解决的问题。

### 最短版介绍

一个用互动案例帮助学生理解“真实工作如何发生”的职业体验平台。

## 3. 项目背景与问题

许多学生对职业的理解主要来自岗位名称、招聘描述、薪资信息和他人经验。即使看过大量介绍，他们仍然很难回答几个更重要的问题：

- 这份工作每天究竟在处理什么问题？
- 工作中的成就感来自哪里？
- 我是否喜欢这种思考、沟通和推进方式？
- 当信息不完整、角色意见冲突时，这个职业如何做判断？

传统职业测试倾向于把用户归类，职业课程则倾向于传授知识。两者都很难让用户在做选择前形成具身理解。

Possibility OS 的假设是：

> 与其继续解释一种职业，不如让用户先完成一小段经过设计的真实工作。

因此，产品把职业探索从“阅读岗位信息”转化为“推进一个工作案例”。用户不需要先掌握专业术语，但会在行动中体验这个岗位如何理解问题、协调他人、生成产物和验证结果。

## 4. 产品定位

Possibility OS 不是：

- 职业性格测试
- 求职培训课程
- 标准答案练习题
- 模拟经营游戏
- 依靠得分、好坏结局或能力值驱动的闯关产品
- 对真实岗位的完整培训或资格认证

Possibility OS 是：

- 一组可以独立体验的职业故事
- 一种低压力、低门槛的工作过程模拟
- 一种帮助用户判断自己是否喜欢某类工作方式的体验工具
- 一个把抽象职业能力转化为具体操作、协作和产物的交互系统

核心价值不是告诉用户“你做得对不对”，而是让用户感受到：

- 我看见了这份工作真正关心的问题。
- 我的表达和取舍推动了事情变化。
- 我完成了一个只有这个职业才会产出的成果。
- 我能够据此判断自己是否愿意继续探索这个方向。

## 5. 目标用户

### 核心用户

- 正在选择专业、实习或第一份工作的大学生和研究生
- 对互联网产品、组织管理、用户体验等职业感兴趣，但缺少真实接触机会的人
- 不想只做职业测试，希望先“试着工作一次”的探索者

### 用户核心需求

- 快速建立对岗位真实内容的具体认知
- 在没有专业经验和求职压力的情况下尝试一段工作
- 感受职业中的思考方式、协作方式与成就感来源
- 用亲身体验补充职位介绍和他人建议

## 6. 整体体验架构

### 6.1 职业大厅

职业大厅是所有故事的入口。它不展示“匹配度”，而是让用户根据兴趣主动选择一种工作。每张职业卡提供：

- 职业名称与一句价值描述
- 本次案例会处理的问题
- 核心工作动作
- 简化的体验路径
- 独立保存的体验进度

当前开放：

| 职业 | 核心命题 | 体验路径 |
| --- | --- | --- |
| 产品经理 | 把模糊问题推进成可验证方案 | 读任务 → 找根因 → 做验证 → 交复盘 |
| HRBP / 员工关系 | 从信息差走到员工确认的改变 | 听信号 → 多方核对 → 员工面谈 → 行动回访 |

### 6.2 工作空间隐喻

进入职业后，用户面对的不是传统网页导航，而是一张第一人称办公桌和一台模拟电脑。

这个空间隐喻承担三个作用：

1. **建立代入感**：用户不是在阅读课程，而是进入工作现场。
2. **承载工具差异**：邮件、聊天、文档、原型、考勤、人才系统和任务看板各自承担真实职责。
3. **让进度变得可见**：工作不会自动跳到下一页，而是在多个软件与角色之间逐渐形成证据和产物。

物理桌面上的键盘、便签、夹板和显示器不是纯装饰。一部分物件也承担交互入口，例如 HR 工作台旁的纸质调查记录板。

### 6.3 共通职业故事结构

两条职业体验虽然内容不同，但共享同一叙事骨架：

```text
收到一个不完整的工作信号
→ 主动寻找更多信息
→ 区分事实、判断与未知
→ 与不同角色沟通
→ 形成一份可讨论的工作草稿
→ 在反馈中修正方案
→ 生成可见的职业产物
→ 回到真实结果进行复盘
```

这套结构可以继续扩展到用户研究、运营、咨询、教育、公共服务等职业故事。

## 7. 职业故事一：产品经理

### 7.1 案例命题

用户扮演一名产品经理，为大学生设计一个周末决策与出行产品。

问题不是简单地“推荐更多地点”，而是理解一群朋友为什么迟迟无法形成共同计划：预算、时间、体力和偏好等限制散落在群聊里，成员看不见共同点、冲突与妥协成本，投票也可能掩盖少数人的底线。

### 7.2 体验目标

让没有产品经验的用户感受到：

- 模糊想法如何被澄清为具体问题
- 产品方向为什么需要目标用户、场景和最小价值
- 功能不是越多越好，而要服务于可验证假设
- PRD、流程图和原型是帮助团队讨论的工具
- 用户数据如何反过来改变原型设计
- 产品经理的核心价值是组织问题、取舍与协作，而不是独自想创意

### 7.3 工作软件

| 软件 | 在体验中的职责 |
| --- | --- |
| Inbox | 接收项目背景和今天的任务 |
| Campus Chat | 与 Mentor、设计、开发和业务角色沟通 |
| Product Docs | 形成产品方向、PRD、范围和验收标准 |
| Figma Design | 生成并编辑低保真流程与可点击原型 |
| Delivery Folder | 汇总产品预览、PRD、流程、反馈、测试证据和复盘 |

### 7.4 核心流程

1. 阅读任务邮件，理解“大学生周末决策”这一模糊业务问题。
2. 在 Chat 中用自然语言表达产品想法，由 Mentor 追问目标用户、真实场景和最痛的一步。
3. 将确认后的方向整理为结构化草稿：目标用户、痛点、第一版价值。
4. 在 Docs 中生成并编辑 PRD，明确 MVP、用户故事、成功指标、验收标准和暂不做内容。
5. 把 PRD 发给 Mentor 评审，再逐条吸收反馈形成新版本。
6. 在模拟 Figma 工作台中生成页面流程、编辑 Frame、连接交互并进入 Present 模式体验。
7. 接收设计、开发和业务反馈，识别体验风险与范围问题。
8. 阅读 20 组模拟灰度测试数据，定位方案确认阶段的主要流失。
9. 根据数据创建原型 v2，补充共同点、冲突、个人妥协成本以及接受 / 替代 / 否决机制。
10. 在交付文件夹中查看最终产品预览、PRD、流程、反馈、数据证据和职业体验总结。

### 7.5 用户最终得到的成果

- 一份可阅读的 PRD Draft
- MVP 功能范围与暂不做清单
- 一条完整用户流程
- 一组低保真原型 Frame
- 一次跨角色评审记录
- 一次基于测试漏斗的数据迭代
- 一个面向用户的产品预览
- 一份产品经理职业体验总结

### 7.6 作品集应强调的设计决策

- 没有用方向卡片替用户做选择，而是从用户自然表达开始。
- 将 Mentor 的“启发和纠偏”与生成器的“结构化整理”概念分开。
- 原型不是静态成果：用户必须编辑 Frame、连接交互、预览，再根据数据生成 v2。
- 最终交付页同时展示用户产品与团队工作产物，让成就感来源于“完成了完整工作链”，而非通关动画。

## 8. 职业故事二：HRBP / 员工关系

### 8.1 案例命题

用户扮演一名 HRBP，处理 CASE 07：主管认为资深门店顾问小林近期业绩、出勤和主动性下降，担心他准备离职。

这个判断只是一个管理信号。随着用户查看正式记录、联系不同角色并与员工沟通，问题逐渐从“员工态度下降”转化为两个组织机制缺口：

- 近四周发生 6 次临时调班，其中 5 次通知不足 24 小时，门店没有统一的提前沟通规则。
- 小林去年参加储备店长项目且业务能力达标，但员工反馈任务因没有指定负责人而停滞 248 天。

小林的核心感受是：公司在缺人时总能想到他，却在他需要发展反馈时长期没有回应。

### 8.2 体验目标

让用户理解 HRBP 的专业价值不只是“和员工聊天”，而是：

- 不把主管标签直接当作事实
- 从多方信息和正式系统中交叉核实
- 理解员工经历而不过度承诺
- 管理信息使用边界
- 把员工诉求转化为责任人、期限和验证标准
- 在行动之后重新回到员工身边，确认体验是否真实改变

### 8.3 工作软件

| 软件 | 在体验中的职责 |
| --- | --- |
| Mail | 接收主管信号与员工关系规则 |
| People Chat | 联系 Mentor、主管、同事与人才伙伴 |
| WorkTime | 核对考勤、排班变更和通知时间 |
| Talent | 查看储备店长评审和中断的反馈流程 |
| Docs | 共创面谈方案、形成纪要与专业研判 |
| Meet | 安排员工面谈和 DAY 14 回访 |
| Tasks | 对齐责任人、期限和验证证据 |
| Drive | 汇总完整案例交付包 |

### 8.4 核心流程

1. 阅读周店长邮件，将“主动性下降”保留为待验证判断。
2. 向 Mentor 了解面谈前应如何区分已知、未知和信息边界。
3. 与主管、同班同事和区域人才发展伙伴沟通。
4. 在 WorkTime 中核对 6 次临时调班、5 次不足 24 小时通知、2 次迟到和销售完成率变化。
5. 在 Talent 中发现评审结论已完成，但员工反馈因没有负责人而停滞 248 天。
6. 将来自不同软件的线索摘录到桌面纸质调查记录板，区分事实、员工体验和工作假设。
7. 在 Docs 中形成面谈目标、事实开场、开放问题、同步边界和回访承诺，并让 Mentor 审阅。
8. 进入线下面谈。电脑缩小为 HR 的实时纪要工具，小林在会议桌对面与用户面对面交流。
9. 通过固定但自然的六个沟通节点了解排班经历、具体影响、发展反馈、公平感、员工诉求和信息边界。
10. 会后将谈话整理为可核实事实、员工关注、关键原话、可同步范围和待验证事项。
11. 创建组织行动：DAY 1 对齐排班规则；DAY 4 完成发展反馈；DAY 14 回访员工；DAY 30 持续复查。
12. 回到小林身边验证行动是否真的改变员工体验，再将案例归档到 Drive。

### 8.5 关键案例结论

| 初始判断 | 核实后的问题 |
| --- | --- |
| “小林主动性下降，可能想离职。” | 临时调班缺少提前沟通规则；储备店长发展反馈因责任人缺失而中断。 |

员工提出的可行动诉求：

- 非紧急调班尽量提前 48 小时沟通，并允许员工说明困难或拒绝。
- 正式反馈优势、差距与下一次发展机会，不让员工长期等待和猜测。

信息使用边界：

- 只向责任人同步解决排班和发展反馈所需的信息。
- 不逐字转述家庭细节。
- 不承诺绝对保密，也不承诺晋升结果。

### 8.6 用户最终得到的成果

- 调查记录与证据摘录
- 面谈方案与 Mentor 反馈
- 员工面谈纪要
- 主管沟通摘要
- 行动跟踪表
- 员工回访记录
- CASE 07 闭环交付包

### 8.7 作品集应强调的设计决策

- 把 HR 体验从“一场线上聊天”扩展成完整的调查、面谈、行动和验证闭环。
- 取消好结局 / 坏结局。用户不足之处由过程中的专业指导承接，不在结尾惩罚。
- 不使用对话选项。当前未接入真实 AI，因此每轮以只读的自然语言预填话术模拟真实交流，避免让用户误以为系统能理解任意文本。
- 面谈从电脑聊天切换为第一人称线下空间；电脑只显示实时纪要和 HR 观察，不重复对话聊天记录。
- 纸质记录板把跨软件信息变成一个持续存在的工作对象，也提醒用户事实、体验和假设不能混写。
- 闭环由员工体验验证，而不是以“任务已完成”或主管确认作为终点。

## 9. 关键产品与交互原则

### 9.1 体验工作，而不是学习知识点

专业解释不应大面积脱离场景出现。提示被放进 Mentor 反馈、软件状态、观察评论、记录板和交付物中，让用户一边工作一边理解为什么。

### 9.2 用产物建立成就感

每段体验都以职业产物收束：产品经理得到 PRD、原型与测试迭代；HRBP 得到纪要、主管摘要、行动跟踪与员工回访记录。

### 9.3 不用游戏结局评价复杂工作

真实职业判断通常没有唯一正确答案。产品避免分数、等级、好坏结局和隐藏数值，把反馈放在过程里，把结尾留给事实、行动和复盘。

### 9.4 自然语言优先，但诚实表达原型能力

界面避免用选项按钮代替表达。与此同时，当前 Demo 没有真实大模型能力，因此必须清楚控制用户预期：

- 产品经理模块使用本地规则和结构化模板模拟 AI 辅助工作流。
- HRBP 模块使用预先写好的自然语言输入与固定输出展示完整沟通。
- 作品集中不得宣称已经接入真实 AI、能够理解完全自由输入或动态生成任意职业故事。

### 9.5 多软件不是关卡列表

软件代表工作工具，而不是线性章节。用户可以返回邮件、正式记录和聊天反复核对；系统用轻量提示指向下一项有意义的工作，而不是把所有应用锁成关卡。

### 9.6 进度由工作状态产生

状态不是抽象百分比，而是：邮件是否已读、证据是否核对、草稿是否审阅、原型是否预览、责任人是否确认、员工是否回访。

## 10. 视觉与空间语言

### 当前整体方向

项目采用温暖、复古、带有轻微纸张和木质感的办公世界：

- 暖米色、木质棕、琥珀色、深青绿和深墨色
- 第一人称办公桌与显示器
- 带实体感的键盘、便签、纸张、夹板和文件标签
- 清晰锐利的工作 UI 与较柔和的空间背景并置
- 克制的圆角、边框、阴影与轻微手绘感

该语言希望传达：工作是具体的、有人参与的、可以被亲手推进的。

### 产品经理空间

产品经理工作台偏深青绿和多软件协作感。模拟 Figma、Docs、Chat 和交付文件夹形成可辨识但统一的工具系统。

### HRBP 空间

HRBP 使用更温暖的琥珀色和纸质记录语言。普通阶段是工作电脑与实体记录板；面谈阶段切换到会议室第一人称空间。

### HR 视觉重构状态

HR 的业务内容和交互链路已经形成，但以下视觉尚未定稿：

- 会议室背景的空间感
- 会议桌的颜色、透视和前后比例
- 电脑在会谈场景中的尺寸与位置
- 小林的人物精度、身体比例和八种情绪状态
- HR 各软件与会谈场景之间的整体一致性

已单独准备 Google Stitch 重构提示词：`docs/stitch-hr-ui-redesign-prompt.md`。在新视觉素材适配完成前，不应使用当前 HR 会谈画面作为作品集 Hero。

### 状态策略

- 产品经理和 HRBP 使用不同的 LocalStorage key，互不覆盖。
- 每条职业体验会保存当前软件、已完成动作、对话进度和生成产物。
- 页面刷新后可以继续体验。
- 当前版本无账号、云同步、服务端数据库和真实多人协作。

### 模拟 AI 的实现边界

当前原型通过以下方式模拟 AI 辅助工作：

- 固定案例上下文
- 预设角色对话脚本
- 基于关键词与当前阶段的本地规则
- 结构化模板生成 PRD、流程、纪要和总结
- 延迟回复与输入预填营造自然对话节奏

这样可以在没有模型服务的情况下验证体验结构，但不等同于真实生成式 AI。

### 验证方式

项目包含 Playwright 流程脚本，用于检查：

- 关键软件和页面是否可到达
- HR 调查、面谈、纪要、行动和回访是否可以完整闭环
- 面谈与后续沟通是否使用预填自然语言而非选项分支
- 交付物是否生成
- 桌面、平板和移动端是否出现明显横向溢出

## 12. Vibe Coding 过程中值得呈现的挑战

### 挑战一：如何模拟真实工作，又不把体验做成繁重培训

解决方式：保留岗位最具代表性的判断、协作和产物，压缩重复劳动与专业门槛。用户做的是少量但完整的关键动作。

### 挑战二：如何避免“选择题式互动”

解决方式：用自然语言输入框承载表达，让用户感觉自己在工作沟通；在未接入 AI 的 HR 模块中，则通过固定预填话术诚实控制能力边界。

### 挑战三：如何让多软件协作不变成机械跳页

解决方式：让同一条信息在邮件、聊天、正式系统、记录板和文档之间流动。用户返回不同工具是为了核实和推进，而不是完成页面打卡。

### 挑战四：如何表现 HR 工作的专业价值

早期版本过度集中在员工面谈，容易像聊天游戏。后续将体验扩展为：多方核实、共创面谈、信息边界、组织行动和员工回访，最终由员工体验验证闭环。

### 挑战五：如何用纯前端承载复杂状态

解决方式：将每条职业故事组织为可持久化状态机；所有软件读取同一案例状态，不同操作会影响其他工具中的提示、内容和产物。

## 15. 推荐截图说明文字

未来截图完成后，可以使用以下 Caption：

1. **职业大厅**：用户不是接受职业匹配，而是主动选择一段想亲自体验的工作故事。
2. **产品经理方向对话**：Mentor 不替用户给答案，而是帮助一个模糊想法逐渐具备用户、场景与可验证价值。
3. **产品经理原型工作台**：PRD 被转化为可编辑、可连接、可预览的低保真流程，用户需要真正修改一次 Frame。
4. **数据迭代**：测试结果不是结尾数据，而是直接进入设计工具，推动共识方案从 v1 变成 v2。
5. **产品交付包**：最终成果同时包含用户可见产品和团队工作产物，让职业成就感变得具体。
6. **HR 初始信号**：主管邮件只提供需要核实的线索，不自动成为对员工的判断。
7. **HR 调查记录板**：不同软件中的正式记录、现场信息和工作假设被放到同一张可持续更新的纸面上。
8. **HR 线下面谈**：电脑退到辅助位置，用户真正面对员工；屏幕承担实时纪要，而不是复制一场线上聊天。
9. **HR 会后研判**：谈话被转化为事实、诉求、原话、信息边界和仍待验证的问题。
10. **HR 闭环**：案例不以“面谈完成”结束，而是以责任人行动和员工确认的体验变化形成闭环。

## 16. 作品集中的事实边界

### 可以明确表达

- 这是一个可运行的 React / TypeScript 前端原型。
- 当前包含两条完整程度不同、但可以独立保存进度的职业故事。
- 产品经理体验覆盖问题定义、PRD、原型、评审、测试数据和迭代。
- HRBP 体验覆盖多方核实、面谈设计、员工沟通、会后研判、组织行动和员工回访。
- 使用固定数据、本地规则与脚本对话模拟 AI 辅助工作。
- 使用 Playwright 验证关键流程和响应式行为。

### 不应虚构

- 不宣称已经接入真实大语言模型。
- 不宣称能够理解任意自由输入。
- 不宣称已有真实学校、企业或大规模用户部署。
- 不虚构完成率、满意度、留存、访谈人数或商业结果。
- 不把 20 组灰度数据描述为真实线上实验；它是产品经理职业故事中的模拟案例数据。
- 不把当前未完成的 HR 视觉当作最终设计成果。

如果未来产生真实用户研究或可用性测试，应在作品集中单独补充样本、方法、发现和改动，不与模拟案例数据混写。

## 17. 当前限制与下一步

### 当前限制

- 没有真实 AI、后端、账号和云同步。
- 职业内容目前直接编写在前端组件中，尚未形成通用内容配置系统。
- 两条职业故事的交互成熟度和视觉完成度不完全一致。
- HR 会谈人物与空间仍在重构。
- 还没有真实目标用户研究和可用性数据。
- 当前页面主要针对桌面端职业工作空间设计，移动端属于适配而非最佳体验。

### 下一步方向

1. 完成 HR 视觉系统、人物表情素材和会谈空间重构。
2. 将职业故事抽象为可配置的案例引擎，减少新增职业时的重复开发。
3. 接入真实 AI 后，将“固定模拟”升级为受边界约束的自然语言互动。
4. 增加内容安全、事实核验和职业专家审阅机制。
5. 进行学生用户测试，验证用户是否更理解岗位、是否感受到职业成就感、是否愿意继续体验其他职业。
6. 增加体验摘要、个人偏好反思和跨职业比较，但避免重新变成职业匹配测试。
7. 继续补齐键盘操作、屏幕阅读器信息和移动端可访问性。
